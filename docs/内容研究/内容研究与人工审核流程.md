# 内容研究与人工审核流程

适用范围：Quick Get Well 的文章、示例消息、Finder 组合文案、完整邮件、下载卡片及对外审核声明。初始状态：未记录真人签核。

## 1. 每项选题先写研究简报

按以下字段建立一条记录，事实、推断和设计选择分别写：

| 字段 | 要填写的内容 |
|---|---|
| 任务 | 谁在什么情况下，要给谁传达什么，当前在哪一步困难 |
| 直接证据 | GSC 原始查询及范围、真实用户的原始表达或实际行为 |
| 反例 | 这个方案在哪些情况下不适用；使用者现有替代办法 |
| 来源 | URL、责任作者/机构、发表或复核日期、访问日期、具体支持的论点 |
| 证据限制 | 身份未验证、旧帖、样本小、厂商自述、是否只看到摘要 |
| 内容或原型 | 为什么这一份内容能帮助任务；明确仍是假设的部分 |
| 验证方式 | 由谁读、让谁用、看什么行为、什么结果会使我们修改或停止 |

来源选择顺序：本站真实行为与具体问题；有编辑责任的写作资料；适用场景的专业机构沟通指南；有完整上下文的公开亲历讨论；产品目录。这个顺序不是绝对的权威排名——产品是否存在、语言是否得体、需求有多大，需要不同来源回答。

不接受为主证据：没有打开正文的检索摘要、无法追溯的祝福聚合页、虚构调查、厂商未交代方法的比例、AI 模拟用户、自动生成的“用户评价”。公开帖子只能证明该表达可见，不能证明作者身份和情节真实。

## 2. 先整理原则，再起草

来源记录应说明借鉴的是哪项原则以及适用范围。癌症或临终沟通资料不能不加区分地套用到普通感冒、儿童卡片或商务邮件。不同来源有分歧时保留分歧，交由编辑按场景判断。

AI 可帮助整理问题、记录来源和准备草稿，但不得自行标记人工已审。现有生成内容不得倒填虚假的参考来源；后续验证说明为“事后核对沟通原则”。不复制他人的例句列表或独特段落，不以替换称呼完成所谓原创。

每份草稿标明：AI 是否参与、作者身份是否已知、参考材料、适用人群、状态、版本。原有文章没有来源记录时写“来源未核实”，不要推断它是人工或 AI 创作。

## 3. 真人英语编辑审核

先选具有成熟英语编辑能力的人。是否具备相关编辑经验要可核实；AI 代理、自动检测器或项目中的另一个模型不算真人编辑。

逐项检查：

- 自然英语：朗读是否像真实交流，称呼、时态、指代、惯用语是否准确。
- 发信人角色：个人、全班、家长、公司团队是否被明确区分，是否无意代表了别人。
- 事实前提：共同回忆、附件、探访、已确认的安排、可提供的帮助是否真实；脱离导语复制是否会误用。
- 收信人感受：是否催恢复、催回复、要求安慰发送者、强迫积极或以痛苦为笑点。
- 承诺边界：不能保证健康结果；不能代替雇主、客户或家人许诺安排。
- 内容价值：保留必要的通用好句，删除只为增加条数的重复；不为去重把自然句子改得生硬。

编辑可以保留、修改或删除，并写理由。需要大改的内容不算批准；修改后请原审核人确认对应部分。

## 4. 场景读者检查与真实任务研究

英语编辑负责语言，不自动具备所有关系场景经验。请教师/家长看教师用语，有相关家庭照护经历的人看亲属用语，熟悉客户沟通的人看商务内容。严重病情内容如需专业审核，应明确专业范围；普通场景读者不能被称为临床审核人。

建议首轮约 6–8 人，作为探索性取样，而非有统计代表性的调查：例如 2–3 位近期给教师/同事写过关怀信息的人、2 位处理客户沟通的人、2–3 位给亲友写过或收过类似信息的人。若某一类招不到人，就把该类验证留空，不能用别类替代。避免把学生、低龄儿童、大学教授三种情境混为一组。

只邀请自愿参与者；不需要诊断、联系方式或对方的私人病情。若对方愿意展示过去的信息，让其先遮去姓名、联系方式与健康细节。未经单独授权不收集、转发或上传私人通信。当前没有招募或联系任何人。

### 访谈提纲：先问经历，再展示页面

1. 最近一次遇到这个情境是什么时候？你当时想表达什么？可以只说关系和沟通场景，不说病情。
2. 你实际用了短信、邮件、纸卡还是电子卡？为什么选它？
3. 你当时怎样找措辞，哪些词犹豫过？最后用了什么类型的表达？
4. 是否找过现有模板？具体哪里有用或没用？没找过也是有效答案。
5. 如果是群体表达，实际有多少人、是否在同一地点、谁收集文字和签名？
6. 原方案里最耗时或最让你拿不准的步骤是什么？有什么无需新工具的解决办法？
7. 再展示现有页面：让参与者为一个相近但不涉及私密信息的场景选择并改写一条内容，记录犹豫、误选和改动。
8. 最后才比较完整邮件、纸卡、电子卡等选项：哪些真的会用，哪些不会？如果不会，为什么？

不问引导性问题，例如“我们的 PDF 是不是很方便”“如果有 AI 工具你会不会用”。不要将礼貌赞同或假设性购买意愿当成已使用。

### 任务观察与决定

记录参与者能否选对身份、删改不真实前提、完成文字、正确复制/打印；将单纯点击与真实完成分开。语言造成严重误解、错误承诺或不适应立即返修，不需要等到多数人都遇到。

对新功能，先要求出现独立的重复任务、现有办法的具体困难以及实际尝试后的收益，再决定是否扩大。人数、时间或通过率阈值须在测试前由团队说明只是产品决策标准；几位参与者的成功不能推出市场占比。

## 5. 签核与版本记录

所有真人意见记录在本项目内，审核人可使用可追溯的编辑署名；身份由项目负责人私下核实，无需存身份证件等敏感资料。

每条记录至少包括：实际审核人/角色、日期、审核范围、所看版本、具体问题与处理、修改后确认、最终决定。未完成时保持 pending，审核人和日期留空。不要使用“团队审核”掩盖无人实际负责。

中央登记为 `review-register.json`。截至 2026-09-22 本轮关键词优化后，37 项全部待审：34 文章 + 共享模板/Finder + 两份 PDF。工作单的五页批准不能替代其他 29 篇或动态生成内容的审核；较早工作单是历史快照，后续变化见 `../关键词研究/2026-09-22-需求驱动内容优化记录.md`。

命令：

```sh
# 获取当前内容指纹；不会生成批准记录
node scripts/check-editorial-review.js --snapshot

# 核对真人签核字段、记录文件与版本；当前预期失败
npm run check:editorial

# 人工审核完成后才用于正式发布
npm run build:release
```

真实审核完成后，再把对应项的 `status` 设为 `human_approved`，填入 `reviewer`、`reviewedAt`（YYYY-MM-DD）、`reviewRecord`（项目内实际意见文件路径）、`reviewedSha256`（真人实际审阅的版本指纹）。`snapshotSha256` 只是建立登记时的快照，不能作为批准。

不要为了让命令通过而补写人名、日期或虚构记录。该脚本只能检查记录和版本，不会核验身份，也不能证明审稿充分。负责人要控制登记修改权限并复核真实意见。

文章指纹覆盖完整页面数据；共享模板/Finder 指纹覆盖两个来源文件。当前实现偏保守，共享代码的纯技术变化也会使其指纹失效；应由负责人确认变化范围并保留说明，不能由 AI 自动沿用批准。PDF 内容变化同样需要重新确认。

远程 Cloudflare 设置尚未更新。要让自动部署实际执行检查，需将正式构建命令设为 `npm run build:release`；在此之前，普通 `npm run build` 不构成发布审核门禁。本轮没有修改远程设置，也没有推送。

## 6. 发布后的验证

审核通过是语言与适用性检查，不是需求或 SEO 效果保证。按页面记录实际发布日期与抓取时间，分别看：

- 任务效果：参与者反馈、选句/改写的成功，真实使用；复制或下载点击只作为辅助行为。
- 获客效果：相同窗口下的相关查询、落地页点击、展示与构成变化。
- 风险反馈：用户指出的语义错误、角色不匹配或不真实前提，优先修正并记录。

当前全站样本很小，不用几天的百分比波动下结论，也不声称从一次同时修改标题、内容和内链的发布中分离出了各自效果。
